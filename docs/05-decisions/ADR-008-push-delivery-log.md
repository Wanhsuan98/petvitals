# ADR-008: 逐台裝置記錄推播結果，並由手機回報收到

Status: Accepted
Introduced: v1.2.0

## Context

使用者回報提醒推播「只有設定那天收得到」。查資料庫時發現 `reminder_schedules.last_sent_on` 每天都有更新、cron 也每天有跑，但這個欄位只代表「伺服器呼叫過發送」，回答不了真正需要的問題：

- 同一則提醒有兩台裝置時，哪一台成功、哪一台失敗？
- 推播服務（Apple / Google）收下之後，手機到底有沒有收到？

先前的修正改成「至少一台送達才標記已發送」，但只要有一台成功，失敗的那台當天就不會再重試；而且仍然只有一個「今天送過了沒」的布林值，無法排查。

## Decision

新增 `push_deliveries` 資料表（`20261028000000_add_push_deliveries.sql`），一列代表「某則提醒、某一天、某一台裝置」的投遞：

1. **逐台去重與重試**：唯一約束 `(reminder_id, subscription_id, sent_on)`。cron 用 `insert ... on conflict do nothing` 搶下投遞權才發送；失敗的裝置用「狀態與次數都沒變才更新」的條件式 update 重新搶下，在同一個 5 分鐘區間的後續觸發重試（約 5 次）。已送達的裝置不會重送。這同時取代了原本「先查 `last_sent_on` 再寫入」的非原子判斷。
2. **手機回報收到**：推播內容帶 `deliveryId`，`public/sw.js` 顯示通知後呼叫 `POST /api/push/ack` 寫入 `received_at`。
3. **通知中心顯示最近 10 筆推播紀錄**（本人所有裝置），把狀態翻成排查結論：
   - 推播服務拒收（附狀態碼與原因）
   - 訂閱已失效（系統已自動移除）
   - 推播服務收下、手機沒有回報收到
   - 手機已收到（仍看不到就是系統通知設定或專注模式）
4. 測試通知也寫入同一張表（`kind = 'TEST'`），每按一次新增一列。
5. `last_sent_on` 保留為摘要（今天至少一台送達過），不再用來決定是否重送。

### `/api/push/ack` 不要求登入

Service Worker 在背景被喚醒時 session 可能已過期，要求登入的話回報會被擋掉，紀錄上就分不出「手機沒收到」和「收到了但回報不了」。改以 `deliveryId` 當憑證：它是隨機 UUID，只出現在加密的推播內容裡；這個端點只能把 `received_at` 從空值寫入，不能讀任何資料，一律回 204、不透露 id 是否存在。被濫用的最壞情況是某筆紀錄被誤標為「已收到」。

## Consequences

- **個資最小化**：只存推播服務主機名稱（例如 `web.push.apple.com`），不存完整 endpoint（等同推播憑證）；錯誤訊息截斷在 300 字內。紀錄保留 30 天，cron 每天 03:00 清除。RLS 只讓本人讀自己的紀錄，寫入一律經由 service role。
- 「手機已收到」代表 Service Worker 收到推播並呼叫了顯示通知，不代表使用者看到了；系統層的通知設定與專注模式仍然無法從伺服器得知，這是 Web Push 本身的限制。
- 手機回報需要新版 `sw.js`；手機上還在跑舊版 Service Worker 時，紀錄會停在「手機沒有回報收到」，重新開啟 App 後才會更新。
- 部分裝置失敗時會在同一個 5 分鐘區間內重試；區間結束仍失敗，那台裝置當天就不會收到這則提醒。
- 一次 cron 觸發要多做「搶投遞權」的查詢（每台裝置 1–3 次資料庫往返）。目前使用者與裝置數很少，成本可以忽略；規模變大時需要改成批次處理。
